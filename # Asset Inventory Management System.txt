# Asset Inventory Management System (AIMS)

## Project Overview

Build a production-ready **Asset Inventory Management System (AIMS)** using:

* Laravel 12+
* PHP 8.3+
* MySQL (XAMPP)
* Bootstrap 5 or Tailwind CSS
* Laravel Eloquent ORM
* Laravel Authentication & Authorization
* DataTables
* SweetAlert2
* AJAX-based CRUD Operations
* Responsive UI/UX
* Clean Architecture
* Service Layer Pattern
* Role-Based Access Control (RBAC)
* Audit Logging
* Asset History Tracking

The system will be used by the IT/MIS Department to manage and track company assets, assignments, accountability documents, employee ownership records, and complete asset lifecycle history.

The system must be scalable, maintainable, production-ready, and follow Laravel best practices.

# User Roles

Implement Role-Based Access Control (RBAC).

## 1. Admin

Full System Access

Can:

* Manage users
* Manage assets
* Manage employees
* Assign assets
* Upload accountability documents
* View audit logs
* View asset history
* Export reports
* Configure system settings

---

## 2. MIS

Functionally identical to Admin.

Purpose:

* Represents MIS Department personnel responsible for maintaining the Asset Inventory System.
* Has all permissions available to Admin.

Can:

* Manage users
* Manage assets
* Manage employees
* View reports
* Manage accountability documents
* Access all modules

---

## 3. Staff

Limited Access

Can:

* View assets
* View assigned assets
* View employees

Cannot:

* Create users
* Delete users
* Add assets
* Delete assets
* Modify assignments
* Access settings

# Future-Proof Architecture & Maintainability Requirements (Critical)

This system will be maintained and expanded by different programmers in the future. Therefore, the codebase must be designed for long-term maintainability, scalability, and ease of customization.

The architecture should prioritize readability and modularity over short-term development speed.

---

# Development Philosophy

Build the system as if it will continue to evolve for the next 5-10 years.

Future developers should be able to:

* Add new asset categories
* Add new modules
* Modify existing workflows
* Add integrations
* Change UI designs
* Add reports
* Add approval systems
* Add API integrations
* Add notification systems
* Add mobile applications

without requiring major rewrites of existing code.

---

# Modular System Architecture

The system must follow a modular architecture.

Each major module should be isolated.

Example Modules:

* Authentication
* Dashboard
* Assets
* Asset Assignments
* Asset History
* Employees
* Employee Documents
* Users
* Roles & Permissions
* Reports
* Audit Logs
* Settings

Each module should have its own:

* Controllers
* Models
* Requests
* Services
* Repository Classes
* Views
* Routes

Future developers should be able to add a new module with minimal impact on existing modules.

---

# Service Layer Pattern

Business logic must NEVER be placed directly inside controllers.

Controllers should only:

* Receive requests
* Validate requests
* Call Services
* Return responses

All business logic should exist inside Service Classes.

Example:

AssetService

EmployeeService

AssignmentService

ReportService

UserService

HistoryService

AuditLogService

This makes future modifications significantly easier.

---

# Repository Pattern

Database operations should be abstracted using repositories.

Avoid placing complex database queries directly inside controllers.

Example:

AssetRepository

EmployeeRepository

UserRepository

AssignmentRepository

HistoryRepository

This ensures future database changes can be handled without modifying business logic.

---

# Configuration Driven Design

Avoid hardcoded values.

Store configurable values inside:

* Database settings table
* Laravel config files
* Enum classes

Examples:

Asset Statuses

Roles

Employment Statuses

Asset Categories

Document Types

Notification Settings

System Settings

Future developers should be able to add new values without changing core application logic.

---

* ECC RAM

Router:

Printer:

* Print Count

Design specifications using flexible relational tables or JSON-based specifications where appropriate.
